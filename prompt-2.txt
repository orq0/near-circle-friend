## 1. Objective

Implement a functional Messenger-inspired prototype featuring an interactive proximity radar powered by **real PostgreSQL/PostGIS geospatial queries**.

The core demonstration must allow a user to activate Near-Circle, discover nearby friends who have opted into discovery, and select individual friends to view proximity information.

This is a working prototype, not a static UI mockup. Social identities and friendships are simulated, but proximity calculations must be real.

**Initial geographic coverage: Metro Manila, Philippines.**

## 4. Interactive Proximity Radar

Build a functional radar visualization.

### Radar behavior

- Current user positioned at the center.
- Concentric rings representing configurable distance intervals.
- Nearby opted-in friends displayed as red dots.
- Dots positioned according to actual bearing and distance.
- Radar radius configurable, initially 1 km, with options for 500 m, 2 km, and 5 km.
- Clicking a dot selects the corresponding friend.
- Smooth animations and visual feedback.
- Proper loading, empty, and error states.

Radar placement must be derived from geospatial results rather than arbitrary screen coordinates.

### Friend selection

When a friend is selected, display:

- Simulated name and avatar.
- Approximate distance in meters or kilometers.
- Near-Circle activation status.
- A **View Route** action indicating that pedestrian routing becomes available in Phase 3.

Do not fabricate road distances, walking routes, step counts, or ETA values.

## 5. PostgreSQL/PostGIS Implementation

Implement persistent geospatial functionality using the existing database.

Required capabilities:

- Store simulated users and friendships.
- Store geographic coordinates using SRID 4326.
- Support user-controlled Near-Circle visibility.
- Query nearby eligible friends using `ST_DWithin`.
- Calculate proximity using geodesic distances in meters.
- Calculate relative bearings for radar positioning.
- Apply appropriate spatial indexes.
- Exclude the current user, inactive users, nonfriends, and stale locations according to documented rules.

Use proper migration and seed mechanisms compatible with the existing project.

Use parameterized queries and validate API inputs.

Do not introduce a second database or duplicate the existing persistence architecture.

## 7. Backend API

Implement or extend REST endpoints using existing routing conventions.

Suggested functionality:

- `GET /friends` — retrieve simulated friends.
- `GET /friends/nearby?radius=1000` — return eligible nearby friends with computed distances and bearings.
- `POST /near-circle/toggle` — enable or disable proximity discovery.
- `PUT /location` — update the demo user's simulated geographic position.
- `GET /friends/:id` — retrieve permitted friend information.

Adapt endpoint names to existing project conventions to avoid unnecessary duplication.

The database must be the source of truth for proximity results. The frontend must not rely on a hardcoded list of nearby friends.

For Phase 2, use an explicitly identified local demo-user context. Do not introduce a fake production authentication system.

## 8. Frontend–Backend Integration

Connect the radar interface to the actual Near-Circle API.

Required behavior:

1. User opens the Messenger-style interface.
2. User activates Near-Circle.
3. Frontend requests nearby friends from the API.
4. Backend performs real PostGIS proximity queries.
5. Radar renders the results using calculated distances and bearings.
6. User changes the radius and results update.
7. User selects a red dot.
8. Friend information appears.
9. User can disable Near-Circle, preventing discovery.

Basic refresh or polling is sufficient. WebSockets are optional only if they fit the current architecture without unnecessary complexity.
